#### Индексы
*Будут на лабах*
Кластерный индекс - столбец, по которому сортируются строчки

PK - non-clustered
Unique + FK -> B-tree
Hash - быстрый, но нельзя использовать диапазоны
``` PG
Create[or Replace] Index <имя индекса>
on <таблица> (столбец1, столбец, );
Create Index
ON <таблица> using hash (столбец);
```

```
select ...
from table (index(имя индекса))


select ...
from table Index(0) - не использовать индексы
```


#### Представления (View)
Это форма представления данных из таблицы.

Вытягиваем данные в моменте создания. Структура создалась при первом create.

Зачем???
- Концентрация данных для пользователя.
- Безопасность базовых таблиц

Есть 2 таблицы, вытягиваем столбцы и делаем на их основе представления.
Мы концентрируем для пользователя данные из этой вьюхи так, что бы не было видно оригинальные таблицы.

Можно создавать на основе и других представлений.
Представление данные не хранит, оно их подтягивает при обращении к нему.

Представляем данные по *ANSI*:
- Если представление на основе одной базовой таблицы
- Нет вычисляемых столбцов (Прямое отображение)
- Чтобы не было distinct (неповторяемые данные)
- Есть PK

```
Create View Имя[(столбцы)]
[with encryption]
as
Select ...
from ...
```

Представления менять через триггеры


Пример с добавлением столбца. Структура создалась на первом шаге. Потому после 2ого шага столбец к вьюхе не добавится. Нужно обновить представление.
```
create view v1
as 
select * from Table1;

Alter Table1
add (d int);

Alter view V1
as
select * from Table1;
```

Чтобы удалилось полностью, нужно чтобы и представление не висело.
```
Drop Table <table> Cascade;
```

```
Drop View <Имя view>
```

#### Materialized View PG
Сохраняет в себе не только структуру, но и данные. Обновляет их во время включения или ручками.

Обращения к ним быстрее, так как данные уже хранит

```
Create Materialized View <Название>[(Столбцы)]
as
Select ...;
```

Для обновления используем следующую команду:
```
Refresh Materialized View <Название>;
```
